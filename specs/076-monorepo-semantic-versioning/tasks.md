# Tasks: Monorepo Semantic Versioning & Release Promotion

**Input**: Design documents from `/specs/076-monorepo-semantic-versioning/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md),
[data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: Included and NOT optional. Constitution II — "behavior is not done until tests prove it" —
binds this feature like any other. Every script here decides what version ships and whether a merge is
allowed; untested, it is a gate that cannot be trusted.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies on incomplete tasks)
- **[Story]**: The user story this serves (US1–US4, mapped to spec.md)

## Phase order note

Phases run **US1 → US3 → US2 → US4**, which inverts the spec's P-order for US2/US3 deliberately. The
spec's priorities rank *value*; this ranks *dependency*. The staging pipeline (US2) produces release
candidates whose numbers come from accumulated classifications, so the classification gate (US3) must
be trustworthy first — otherwise the first candidates are computed from unvalidated input. Nothing is
dropped or deferred out of the feature. See plan.md § Phase ordering.

## Phase 4: User Story 3 — Version bumps are earned, computed, enforced (Priority: P3)

**Goal**: No pull request merges without a machine-readable classification; the version it would
produce is visible before merge; no version is ever hand-edited.

**Independent test**: Open a PR with no classification, confirm the merge is blocked with an
actionable message; add it, confirm the gate passes and reports the predicted version. (quickstart
S2, S3)

- [ ] T024 [US3] Create `.github/workflows/version-gate.yml` running on `pull_request` (`opened`, `synchronize`, `reopened`, `edited` — `edited` matters because the title is the input), invoking `classify.js` against the PR title and changed-file list
- [ ] T025 [US3] Make the gate's failure message name the accepted types and the exact edit that fixes it (FR-011), quoting the offending title back
- [ ] T026 [US3] Surface the predicted next version in the check's job summary so the author sees the consequence of their classification before merging (FR-012)
- [ ] T027 [US3] Confirm no `continue-on-error` on any step of `version-gate.yml` and add a comment explaining that this gate may never become advisory (constitution IV, quickstart S2 negative check)
- [ ] T028 [US3] Add a hand-edited-version check to the gate: fail when a PR diff changes a `version` field in any workspace `package.json` other than a mini-app's (FR-008, `contracts/version-scheme.md` §7)
- [ ] T029 [P] [US3] Create `.github/workflows/branch-policy.yml` failing a `pull_request` into `main` whose head is neither `staging` nor `hotfix/*` (FR-018)
- [ ] T030 [US3] Add hotfix drift detection: after a release, detect commits present on `main` but absent from `staging` and report through an issue rather than a log line (FR-019)
- [ ] T031 [US3] Register `version-gate` and `branch-policy` as required status checks in branch protection for `main` and `staging` — a gate that is not required is not a gate

**Checkpoint**: Classifications are trustworthy. Candidate numbering in Phase 5 now has valid input.

## Dependencies

```
Phase 1 (Setup)
   └─▶ Phase 2 (classify.js + version.js)          ← blocks everything
          ├─▶ Phase 3  US1  version identity        🎯 MVP, independently shippable
          │      └─▶ Phase 4  US3  the gate          (needs release.yml from US1)
          │             └─▶ Phase 5  US2  staging    (needs trustworthy classifications)
          │                    └─▶ Phase 6  US4  artifact tracing
          └─────────────────────────────────────────▶ Phase 7  Polish
```

**Story independence**: US1 delivers value alone — production becomes identifiable with no branch or
environment change. US3 is testable against US1's release job. US2 requires US3 only so its candidate
numbers are computed from validated classifications. US4 extends US1's release record.

file existing.

## Implementation strategy

**MVP = Phase 1 + Phase 2 + Phase 3 (US1).** That is 23 tasks and it delivers the feature's core
troubleshooting value: production and any other deployed surface can be asked what they are running,
and every release leaves a record. No branch changes, no new infrastructure, no merge gates.

**Increment 2 = Phase 4 (US3)**, 8 tasks, which makes the numbers mean something.

**Increment 3 = Phase 5 (US2)**, 11 tasks and the only phase with real operational cost — two Cloud
Run services, DNS, and separately funded accounts.

**Increment 4 = Phase 6 (US4)**, 6 tasks, the highest leverage per incident and the right thing to
defer if scope must be cut.

**Total: 52 tasks.**
